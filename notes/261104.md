## PG 결제: 인증과 승인은 왜 나뉘어 있나

### 한 줄 요약
결제창에서 끝나는 건 **인증**(이 카드 주인이 맞다)이고, 실제로 돈이 빠지는 **승인**은 **서버**가 PG사에 따로 요청한다.

### 왜 어려웠나
- KCP 결제창에서 카드 인증까지 끝나면 결제가 끝난 줄 알았다.
- 그런데 흐름에는 "Ret_URL 리다이렉트 → 백엔드에서 실결제"가 한 번 더 있다. 이게 왜 필요한지 헷갈렸다.

### 개념 정리

```
① 거래등록   화면 → PG       "이 주문, 이 금액으로 결제할게요" (금액 고정)
② 인증       사용자 → PG     결제창에서 카드·본인 확인
③ Ret_URL    PG → 화면       "인증 끝났어요" 신호 (아직 돈은 안 빠짐)
④ 승인       서버 → PG       "진짜로 결제해 주세요" → 이때 돈이 빠짐
⑤ 주문 완료  서버 → DB       주문 상태를 '결제 완료'로
```

| 단계 | 누가 | 믿어도 되나 |
|---|---|---|
| 거래등록 | 화면이 요청 | 금액을 PG에 먼저 고정해 위변조를 막는 용도 |
| 인증 결과(Ret_URL) | PG가 화면으로 보냄 | **그대로 믿으면 안 됨**. 사용자 브라우저를 거쳐 오기 때문 |
| 승인 | 서버가 PG에 직접 요청 | **최종 판단 기준**. 서버 ↔ PG 직통이라 중간에 바뀔 수 없음 |

나뉘어 있는 이유:
- **보안**: 브라우저를 거친 값은 조작될 수 있다. 돈이 빠지는 결정은 서버가 PG와 직접 한다.
- **정합성**: 승인과 주문 완료를 서버가 한 흐름으로 처리해야, 중간에 사용자 연결이 끊겨도 "돈은 빠졌는데 주문은 안 된" 상태가 생기지 않는다.

### 내 프로젝트에서는
- 스마트관광에서 처음엔 프론트가 인증 결과를 받고 주문 완료 API까지 불렀다.
- 모바일에서 결제 직후 연결이 끊기면 주문 완료가 빠지는 문제가 생겼다.
- 그래서 승인·주문 완료를 백엔드로 옮기자고 했고, 백엔드 팀과 함께 구조를 바꿨다.
- 다시 보면 이 문제는 **"인증과 승인을 나눈 이유"를 그대로 지키지 않아서** 생긴 것이었다.

### 면접에서 이렇게 말하기
> PG 결제는 인증과 승인이 나뉘어 있습니다. 결제창에서 끝나는 건 카드 인증이고, 실제로 돈이 빠지는 승인은 서버가 PG에 직접 요청합니다. 브라우저를 거쳐 오는 인증 결과는 조작될 수 있고 연결이 끊길 수도 있어서, 최종 판단은 서버가 해야 합니다. 스마트관광에서 프론트가 주문 완료까지 맡았다가 모바일에서 연결이 끊기면 주문이 빠지는 문제를 겪었고, 그래서 백엔드로 옮겼습니다.

### 스스로 확인 질문
1. Ret_URL로 온 결과만 보고 "결제 성공" 화면을 보여주면 어떤 문제가 생길까?
2. 거래등록을 하지 않고 결제창부터 열면 무엇이 위험할까?
3. 승인은 됐는데 주문 완료 저장이 실패하면, 서버는 무엇을 해야 할까? (힌트: 결제 취소 or 재시도)

## Claude Code에서 명령어 쓰는 법과 오류 종류

### 한 줄 요약
Claude Code에서 내가 직접 명령을 돌리려면 입력창 **맨 앞 글자를 `!`**로 쓴다. Claude가 대신 돌리다 막히는 경우는 대부분 **안전 장치**가 막은 것이라, 오류 종류를 알면 무엇을 해야 할지 바로 보인다.

### 왜 어려웠나
- `! cd ...`처럼 앞에 공백이 들어가거나 여러 줄로 붙여넣으면, 명령이 실행되지 않고 그냥 메시지로 전달됐다. 몇 번 헛돌았다.
- Claude가 "자동 승인에서 막혔다"고 할 때, 이게 오류인지, 내가 뭘 해야 하는지 헷갈렸다.

### 개념 정리

**1) `!` 명령 쓰는 법**

```
❌  " !cd ~/study && git push"     ← 맨 앞 공백 → 그냥 메시지로 감
❌  "!cd ~/study && git commit      ← 줄바꿈 → 앞부분만 가거나 메시지로 감
       --amend"
✅  "!cd ~/study && git commit --amend --no-edit --reset-author && git push --force-with-lease"
```

- `!`는 **입력창의 첫 글자**여야 한다. 붙여넣을 때 공백이 같이 들어가면, `!`만 직접 타이핑하고 그 뒤에 붙여넣는다.
- 명령은 **한 줄로**. 여러 명령은 `&&`로 잇는다(앞 명령이 성공해야 다음 실행).
- 실행되면 대화에 `bash-input` / `bash-stdout`으로 결과가 남아서 Claude도 결과를 볼 수 있다.
- 로그인처럼 내가 직접 입력해야 하는 명령(예: `gh auth login`)도 이 방식으로 실행한다.

**2) 오늘 겪은 오류 종류**

| 메시지 | 뜻 | 할 일 |
|---|---|---|
| **Permission denied … [Git Destructive]** | 기록을 덮어쓰는 명령(force push 등)이라 Claude가 대신 못 하게 막음 | 내가 `!`로 직접 실행 (정말 덮어써도 되는지 확인 후) |
| **classifier gave no verdict (error)** | 자동 승인 검사가 일시적으로 응답 없음. 명령이 위험해서가 아님 | 잠시 후 다시 시도. 계속 안 되면 다른 방법(파일 편집 도구 등)으로 |
| **Blocked: sleep … followed by …** | 긴 `sleep`으로 기다리는 걸 막음 | `until <조건>; do sleep 2; done`처럼 조건을 확인하며 기다리기 |
| **Cannot find module '…/scratchpad/…'** | 임시 폴더(scratchpad)가 비워져 스크립트가 사라짐 | 자주 쓰는 스크립트는 저장소 안(`scripts/`)에 두기 |
| **Cannot find module 'puppeteer'** | 스크립트 위치에서 라이브러리를 못 찾음 | 라이브러리가 설치된 프로젝트 폴더에서 실행하거나 `NODE_PATH` 지정 |
| **Shell cwd was reset to …** | 명령이 끝나면 작업 폴더가 원래대로 돌아감 (오류 아님) | 매번 `cd 경로 &&`로 시작하거나 절대 경로 쓰기 |

- 1번처럼 "위험해서 막힌 것"과 2번처럼 "일시적으로 응답이 없는 것"은 다르다. 1번은 같은 일을 다른 방법으로 우회하지 말고 **내가 판단해서 직접** 실행해야 한다.

### 내 프로젝트에서는
- study 저장소 첫 커밋의 작성자를 회사 메일에서 개인 메일로 바꾸려고 했다. 작성자를 고친 커밋을 다시 올리려면 force push가 필요해서 Claude 쪽에서는 [Git Destructive]로 막혔고, `!`로 직접 실행해 해결했다.
- 그 전에 `! cd`(앞 공백), 여러 줄 붙여넣기로 세 번 실행되지 않았다.
- 이력서 PDF 스크립트가 scratchpad에서 두 번 사라져서 `private_resume/scripts/generate-pdf.js`로 옮겼다.
- 참고: 잔디는 커밋 이메일이 GitHub 계정(Settings → Emails)에 등록돼 있어야 잡힌다. 개인 메일을 등록한 뒤 study 커밋이 계정에 연결된 것을 확인했다(`gh api repos/HeeJeShin/study/commits/main --jq .author.login` → `HeeJeShin`).

### 면접에서 이렇게 말하기
> AI 코딩 도구를 쓸 때 위험한 작업은 도구가 대신 하지 못하게 막아 두는 편이 안전하다고 봅니다. 실제로 Claude Code에서 force push 같은 기록 덮어쓰기는 자동으로 막히고, 그런 작업은 제가 확인한 뒤 직접 실행했습니다. 일시적인 오류와 안전 장치가 막은 것을 구분해서, 막힌 작업은 우회하지 않고 제가 판단하는 방식으로 씁니다.

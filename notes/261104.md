# 261104

## PG 결제: 인증과 승인은 왜 나뉘어 있나

### 한 줄 요약
결제창에서 끝나는 건 **인증**(이 카드 주인이 맞다)이고, 실제로 돈이 빠지는 **승인**은 **서버**가 PG사에 따로 요청한다.

### 왜 어려웠나
- KCP 결제창에서 카드 인증까지 끝나면 결제가 끝난 줄 알았다.
- 그런데 흐름에는 "Ret_URL 리다이렉트 → 백엔드에서 실결제"가 한 번 더 있다. 이게 왜 필요한지 헷갈렸다.

### 개념 정리

```
① 거래등록   화면 → PG       "이 주문, 이 금액으로 결제할게요" (금액 고정)
② 인증       사용자 → PG     결제창에서 카드·본인 확인
③ Ret_URL    PG → 화면       "인증 끝났어요" 신호 (아직 돈은 안 빠짐)
④ 승인       서버 → PG       "진짜로 결제해 주세요" → 이때 돈이 빠짐
⑤ 주문 완료  서버 → DB       주문 상태를 '결제 완료'로
```

| 단계 | 누가 | 믿어도 되나 |
|---|---|---|
| 거래등록 | 화면이 요청 | 금액을 PG에 먼저 고정해 위변조를 막는 용도 |
| 인증 결과(Ret_URL) | PG가 화면으로 보냄 | **그대로 믿으면 안 됨**. 사용자 브라우저를 거쳐 오기 때문 |
| 승인 | 서버가 PG에 직접 요청 | **최종 판단 기준**. 서버 ↔ PG 직통이라 중간에 바뀔 수 없음 |

나뉘어 있는 이유:
- **보안**: 브라우저를 거친 값은 조작될 수 있다. 돈이 빠지는 결정은 서버가 PG와 직접 한다.
- **정합성**: 승인과 주문 완료를 서버가 한 흐름으로 처리해야, 중간에 사용자 연결이 끊겨도 "돈은 빠졌는데 주문은 안 된" 상태가 생기지 않는다.

### 내 프로젝트에서는
- 스마트관광에서 처음엔 프론트가 인증 결과를 받고 주문 완료 API까지 불렀다.
- 모바일에서 결제 직후 연결이 끊기면 주문 완료가 빠지는 문제가 생겼다.
- 그래서 승인·주문 완료를 백엔드로 옮기자고 했고, 백엔드 팀과 함께 구조를 바꿨다.
- 다시 보면 이 문제는 **"인증과 승인을 나눈 이유"를 그대로 지키지 않아서** 생긴 것이었다.

### 면접에서 이렇게 말하기
> PG 결제는 인증과 승인이 나뉘어 있습니다. 결제창에서 끝나는 건 카드 인증이고, 실제로 돈이 빠지는 승인은 서버가 PG에 직접 요청합니다. 브라우저를 거쳐 오는 인증 결과는 조작될 수 있고 연결이 끊길 수도 있어서, 최종 판단은 서버가 해야 합니다. 스마트관광에서 프론트가 주문 완료까지 맡았다가 모바일에서 연결이 끊기면 주문이 빠지는 문제를 겪었고, 그래서 백엔드로 옮겼습니다.

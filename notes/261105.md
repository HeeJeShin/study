# 261105

## AI가 만든 코드는 어떻게 검증하나

### 한 줄 요약
AI가 만든 코드도 **사람이 만든 코드와 같은 관문**(규칙 → 타입 체크 → 테스트 → CI)을 통과해야 반영되게 한다. 그리고 정답이 필요한 계산·데이터는 처음부터 AI에게 맡기지 않는다.

### 왜 어려웠나
- AI로 코드를 빨리 만들 수는 있는데, "잘 돌아간다"와 "맞다"는 다르다. 겉보기엔 그럴듯한데 틀린 코드를 어떻게 걸러내야 할지 기준이 없었다.
- 면접(헤루 등)에서 "AI가 만든 코드 품질을 어떻게 판단하나요?"를 물으면, 감으로 본다는 것 말고 구조로 설명해야 한다.

### 개념 정리

**1) 검증은 관문을 겹겹이 두는 것**

```
AI가 코드 작성
   │
   ▼
① 실행 방법 공유(CLAUDE.md) ← 누가 AI를 쓰든 같은 방식으로 테스트를 돌리게
   ▼
② 타입 체크(tsc)        ← API 응답 타입을 먼저 정의해 두면 엉뚱한 필드 사용이 바로 걸림
   ▼
③ 단위 테스트(Vitest)   ← 기대 동작을 테스트로 먼저 고정
   ▼
④ E2E(Playwright)      ← 실제 화면 흐름(검색 → 선택 → 결과)이 끝까지 되는지
   ▼
⑤ CI(GitHub Actions)   ← ①~④를 사람이 빼먹지 않게 자동으로. 통과해야만 배포
   ▼
반영 / 배포
```

| 관문 | 무엇을 막나 | 놓치는 것 |
|---|---|---|
| 실행 방법 공유 | 사람마다 다른 방식으로 테스트하거나 건너뛰는 것 | 테스트 자체의 빈틈 |
| 타입 체크 | 없는 필드, 잘못된 타입 | 값이 틀린 것 |
| 단위 테스트 | 함수·컴포넌트의 잘못된 동작 | 화면끼리 연결 문제 |
| E2E | 실제 사용자 흐름이 깨진 것 | 느리고, 경우의 수를 다 못 봄 |
| CI | 사람이 검사를 건너뛰는 것 | 검사 자체가 부실하면 의미 없음 |

**2) 처음부터 AI에게 맡기지 않을 것을 나눈다**
- AI가 잘하는 것: 해석, 설명, 초안, 반복 코드
- AI에게 맡기면 위험한 것: **정답이 하나인 계산**, **돈·안전이 걸린 사실 데이터**
- 그래서 "AI는 읽고 설명하고, 계산과 사실은 코드와 검증된 DB가 맡는다"로 역할을 나눈다.

### 내 프로젝트에서는
- **어드민시스템**: 팀원 모두 Claude Code를 쓰기 때문에 CLAUDE.md에는 코드 규칙보다 테스트 실행 방법을 정리해 공유했다(폴더 구조나 shared 사용 같은 건 당연한 전제라 따로 쓰지 않았다). API 응답 타입을 먼저 만든 뒤 Zod로 런타임에서도 검증했다. AI가 만든 코드는 타입 체크와 Vitest 테스트 216개를 통과해야 반영했고, 결과는 CSV 리포트로 정리했다. README에 실행 가이드를 남겨 누구나 같은 테스트를 돌릴 수 있게 했다.
- **중구**: Claude Code로 개발하면서 Playwright E2E와 GitHub Actions를 붙였고, CI를 통과해야만 Render가 배포하도록 설정했다. 고질병 같은 사실 정보는 출처가 있어야 '검증됨'으로 저장되게 서버에서 막고, Gemini는 안내만 맡겼다.
- **4J 해커톤**: Gemini는 도면에서 면적·출입구만 읽고, 수용인원 계산은 코드가 기준표로 했다.

### 면접에서 이렇게 말하기
> AI가 만든 코드도 사람이 만든 코드와 같은 관문을 통과해야 반영되게 합니다. 팀원 모두 AI를 쓰기 때문에 테스트 실행 방법을 문서로 공유해 누구나 같은 방식으로 검증하게 하고, 타입 체크와 테스트로 동작을 확인하고, CI에서 이 검사를 자동으로 돌려 통과해야만 배포되게 했습니다. 그리고 계산이나 돈이 걸린 데이터처럼 정답이 필요한 부분은 처음부터 AI에게 맡기지 않고 코드와 검증된 데이터로 처리합니다.

### 스스로 확인 질문
1. 타입 체크를 통과했는데도 틀린 코드는 어떤 경우일까? 무엇으로 잡을까?
2. AI가 테스트 코드까지 만들었다면, 그 테스트는 어떻게 믿을 수 있을까?
3. 내 서비스에서 AI에게 맡기면 안 되는 부분을 하나 골라 이유를 말해보기.
